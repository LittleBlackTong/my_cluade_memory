# 时间获取意识

**TL;DR**：用**方案 C**——会话开始 date 一次记锚点；连续写入复用锚点，直到锚点变可疑（跨午夜/用户提及时间/date 返回异常）时再 date。**不**依赖系统提示里的 `currentDate`，**不**依赖记忆里的"大概日期"。

## 核心规则（方案 C）

1. **会话开始时**：跑一次 date，记下权威锚点（`YYYY-MM-DD HH:MM:SS TZ`）作为本会话时间基准
2. **写入 frontmatter / log.md 前**：
   - **默认**：复用锚点（不再 date）
   - **触发重新 date 的条件**（满足任一即重新 date）：
     - 距上次 date 超过 30 分钟
     - **跨午夜**判断（基于锚点日期 + 估计耗时；如果会话已持续数小时，怀疑日期已变）
     - 用户在对话中**显式提及时间**（"今天"、"刚才"、"明天"）
     - date 返回值与锚点偏差超过预期（如锚点 15:00，重新 date 返回 23:50——确认未跨日）
3. **相对时间表达**（"昨天"、"三天前"、"上周"）：用锚点推算 + 必要时重新 date
4. **跨会话引用**（"上次我们聊过"）：读 log.md 时间戳，不靠记忆
5. **跨时区敏感操作**（截止日期、日程）：配合 `date -u` 或 `TZ=` 环境变量

## 为什么不"每次写入前都 date"

- 性能/噪音：频繁 date 会让对话变啰嗦
- 误判风险：单次 date 也可能因沙箱时钟漂移产生偏差——只要锚点可信，复用就行
- 真正危险的场景是**跨午夜**和**长会话**——这正是触发条件覆盖的场景

## Why

LLM 没有内置时钟。系统提示里的 `currentDate` 是会话开始时的快照，**会话内可能跨越午夜、用户时区、或者系统提示本身就有偏差**。基于"脑子里的时间"推断会导致：

- frontmatter 写错日期
- log.md 时间线错乱，归档顺序失真
- 相对时间引用跑偏

用户在 2026-08-09 明确要求："做事之前，先确认好当前时间，别因为上下文导致你的时间认知是错误的。" 用户在 2026-08-09 选择方案 C（混合策略）以平衡准确性与效率。

## How to apply

**推荐命令**：

```bash
# 默认时区日期时间（锚点用）
date '+%Y-%m-%d %H:%M:%S %Z'

# 仅日期（写入 frontmatter 用，从锚点截取）
date '+%Y-%m-%d'   # 或从锚点直接复用

# 星期几
date '+%A'

# UTC（对比时区）
date -u '+%Y-%m-%d %H:%M:%S UTC'
```

**触发重新 date 的速查清单**：

- [ ] 距上次 date 超过 30 分钟？
- [ ] 会话已经持续数小时，可能跨午夜？
- [ ] 用户消息里出现时间词（今天/刚才/明天/周三）？
- [ ] 我自己即将写"昨天"/"上周"等相对词？

满足任一就 date。

## 边界

- 这条规则**不**适用于纯计算/查询任务（"X+Y 等于多少"）——那些不需要时间
- 如果 bash date 因沙箱权限不可用，**降级**：Python `from datetime import datetime; datetime.now().isoformat()`，但仍要验证它与锚点一致
- **绝不**用"系统提示 currentDate 是 X 所以现在就是 X"——那是会话开始时刻，不是当下
